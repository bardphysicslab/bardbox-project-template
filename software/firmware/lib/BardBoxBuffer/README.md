# BardBoxBuffer

Recording interval, record creation, durable queue and acknowledgement.

| Contract | Overview |
| --- | --- |
| Responsibility | Owns the recording interval and boundaries; at each due boundary takes one snapshot from a `SnapshotSource`, creates one full-node record, persists it, and keeps the latest completed record. Owns FIFO delivery order and acknowledgement |
| Interface | `service(nowMs, source)` (at most one RAM retry and one new record per step), `setAttribution(uid, firmware, protocol)`, `begin(nowMs, bootId, storage, generationSeed)`, `peekOldest(record, token)`, `acknowledge(token)` (`Removed`, `StaleToken`, `Empty`, `StorageError`), where a token is a queue generation plus a sequence, `latest(record)`, `status()` |
| Storage | `StorageAdapter` interface (`BardBoxStorage.h`): `LittleFsStorage` on ESP32 (the `spiffs`-labelled data partition, mounted with format-on-fail off); an in-memory fake on hosts. One immutable file per record (`/bbq/r<seq>`), written to a temp file and renamed, never overwritten; `/bbq/meta` (CRC-checked, temp file and rename) holds the queue generation, next sequence, eviction count and any eviction in progress |
| Framing | Storage frame `BBQ1` \| frame version \| length \| CRC-32 \| payload, separate from any serial wire form. The payload has its own schema version (2 = candidate, not an accepted scientific schema) and carries the queue token, the **original UID, firmware version and wire protocol, and each channel's sensor, measurement, unit and type**, so later configuration changes cannot reinterpret saved values. Unknown acquisition time stays unknown |
| Configuration | `BARDBOX_RECORDING_INTERVAL_S` (seconds, default 60, 5..86400): record creation and admission only. `BARDBOX_BUFFER_CAPACITY_RECORDS` (default 256, 2..1024). `BARDBOX_BUFFER_RAM_RECORDS` (RAM retry slots, default 8, 1..64) |
| Guarantees (host-tested) | Records and FIFO order survive a restart unchanged. Only the exact head token (generation and sequence) removes a record; stale tokens remove nothing. A sequence is reserved in meta before its record is written. A missing or corrupt meta starts a new random generation, so a token from before cannot match a new record; sequence exhaustion starts a new generation only when the queue is empty, otherwise admission blocks (`sequence_exhausted`). More saved records than capacity (or more files than one scan holds) give `over_capacity`: admission blocks and every saved record is still delivered in order before new ones; the next sequence is always above every existing file, and an existing path is never overwritten (`path_conflict`). Eviction writes its intent to meta before deleting, so the loss count is correct after a failure at any step. Write, rename, remove or meta failures keep the record (RAM retry, or still the head; `meta_write_failed` blocks admission until meta is written). Interrupted writes are removed and counted; unreadable records are counted as `quarantined` only when moved aside, otherwise as `unreadable`, and are never delivered. A mount failure never formats |
| Limits | Physical flash durability, power-loss timing and wear are **not verified**; one file per record has unmeasured LittleFS overhead, so capacity is not a retention figure. A lost meta file in an **empty** queue looks like first use, so an earlier eviction count cannot be recovered then (tokens stay safe through the new generation). A random generation collision (about 1 in 2^32) is not excluded. The latest completed record is per boot. Write-failure counts are per boot. A full rescan runs when the in-memory index empties while records remain on disk. Storage writes run on the service task and may delay Serial |
| Dependencies | None beyond its own `StorageAdapter`; defines the shared record schema and `SnapshotSource` |

Shared contract: [serial/base API](https://github.com/bardphysicslab/bardbox/blob/main/docs/firmware-base-and-serial-api.md); [buffer API proposal](https://github.com/bardphysicslab/bardbox/blob/main/docs/firmware-buffer-api.md).

Status: **progress** ([#36](https://github.com/bardphysicslab/bardbox-project-template/issues/36)): implemented and host-tested with simulated values and simulated storage/restarts; built for the Feather ESP32-S3 but not run on hardware. Names, wire forms and behaviors marked candidate are pending review.
